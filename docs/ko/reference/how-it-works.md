# 동작 원리

## 파이프라인

rrweb 녹화는 영상이 아닙니다. DOM 변경 기록의 나열이라서, 픽셀을 얻으려면 실제 브라우저에서 다시 재생하고 그걸 녹화하는 수밖에 없습니다. [`rrvideo`](https://www.npmjs.com/package/rrvideo)가 Playwright로 하는 일이 그것이고, 변환에 실시간이 걸리는 이유이기도 합니다.

```
events → (선택적 슬라이스) → Chromium 재생 → WebM/VP8 → ffmpeg → MP4 또는 GIF
```

## 왜 재인코딩이 필요한가

Playwright 녹화기는 넘겨준 파일 확장자와 무관하게 **VP8/WebM**을 내놓습니다. 그래서 `rrvideo` 결과를 `.mp4`로 저장하면 이름만 mp4인 WebM이 됩니다. Chrome에서는 재생돼서 한동안 문제가 드러나지 않지만, QuickTime, PowerPoint, iOS에서는 열리지 않습니다.

이 도구의 모든 경로는 `libx264` + `yuv420p` + `+faststart`로 끝납니다. PM이 열 수 있는 파일과 못 여는 파일의 차이입니다.

## 긴 세션

1시간짜리 리플레이를 Chromium 하나로 돌리면 끝나기 전에 메모리가 터집니다. 임계값(기본 25분)을 넘으면 세션을 윈도우로 자르고, 각각을 **새** 브라우저 프로세스에서 변환합니다. 그래서 최대 메모리가 세션 전체가 아니라 윈도우 하나에 묶입니다.

임계값 아래에서는 분할이 오히려 손해입니다. 윈도우마다 Chromium 콜드 부팅 비용을 내기 때문입니다. 짧은 세션이 단일 변환 경로로 가는 이유입니다.

## 클립에 트림이 필요한 이유

rrweb은 `FullSnapshot`(`type: 2`)에서만 재생을 시작할 수 있습니다. 완전한 DOM을 담은 유일한 이벤트이기 때문입니다. 그래서 15:00에서 시작하는 윈도우도 그 직전 스냅샷부터 슬라이스해야 하고, 렌더된 클립은 윈도우보다 앞에서 시작합니다. 그 앞부분을 잘라낸 뒤 이어 붙입니다.

트림 길이를 정하는 뻔한 방법은 이벤트 타임라인 계산입니다.

```
trimSec = (윈도우_시작 - 스냅샷_타임스탬프) / speed
```

이건 1초 안팎으로 틀립니다. Chromium이 녹화를 시작한 뒤 실제 재생이 시작되기까지의 리드인을 알 수 없기 때문입니다. 우리가 원하는 구간은 항상 클립의 **뒤쪽**이므로, 렌더된 파일 길이에서 역산하면 정확하고 리드인까지 자동으로 보정됩니다.

```
trimSec = 실제_클립_길이 - (윈도우_길이 / speed)
```

## 세그먼트가 끝까지 WebM으로 남는 이유

`ffmpeg -c copy`는 VP8을 MP4 컨테이너에 쓰지 못합니다. 그리고 VP8을 `-c copy`로 트림하면 키프레임 단위로만 잘려서 prefix가 그대로 남습니다. 그래서 세그먼트마다 트림과 H.264 인코딩을 한 번에 처리하고, 마지막 `concat`만 복사로 끝냅니다.

정확한 트림을 위해 `-ss`는 `-i` **뒤에** 둡니다. 그래야 디코딩 기반 정밀 seek을 씁니다. 앞에 두면 키프레임 단위로 붙습니다.

## GIF

GIF는 256색 포맷입니다. 그냥 인코딩하면 UI 글자가 무너지므로 클립마다 팔레트를 따로 만듭니다.

```
fps=N,scale=W:-1:flags=lanczos,split[a][b];
[a]palettegen=stats_mode=diff[p];
[b][p]paletteuse=dither=bayer:bayer_scale=3
```

`stats_mode=diff`는 변하는 영역에 색을 몰아줍니다. 화면 대부분이 정지인 세션 리플레이에 잘 맞습니다.
